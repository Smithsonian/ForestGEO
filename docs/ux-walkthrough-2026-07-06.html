UX walkthrough · browser-driven audit

Where ForestGEO users get lost, and how to fix it

I drove every major user path in the app with a real browser — login, site/plot/census selection, all eight Census Hub pages, the four fixed-data grids, the upload and manual-entry dialogs, inline editing, the admin area, a page refresh, and a phone-sized viewport. The app's individual screens are mostly in good shape; the confusion concentrates in three places: losing your place on reload, numbers that contradict each other across pages, and power-user internals leaking into scientist-facing screens.

First run & orientation

A new user's first ten minutes: sign in, pick a site, a plot, and a census. The three-step selector is a sound model — but the copy around it contradicts itself and a delete button sits inside the picker.

F1Major

The dashboard says "No Sites Available" while the site selector lists nine

Logged in as a global-role user, the dashboard's Available Sites card says "You don't have access to any sites yet. Please contact an administrator" — while the sidebar dropdown, on the same screen, offers "Allowed Sites (9)". The card reads session.user.sites (explicit grants), the dropdown honors the global role. A global user with no explicit grants gets told they're locked out of a system they fully control.

Fix: resolve the card and the dropdown from the same source. If userStatus === 'global', treat all sites as available in both places — and render the site cards in the dashboard body so the "options below" copy becomes true.

Codex: recommendation is sound. Fix dashboard/site selector parity by sourcing global-admin site visibility from the same all-sites list used by the sidebar.

F2Major

Delete buttons live inside the census picker

Each census card — and even the option row in the census dropdown — carries a live trash-can button. A confirmation modal exists behind it, but the destructive affordance sits a few pixels from the thing users click dozens of times a week. The site dropdown's first group header shouts "DESELECT SITE (WILL TRIGGER APP RESET!)" — internal implementation anxiety leaking into a menu label.

Fix: move census deletion behind the card's edit/manage surface (or Census Overview), not the picker. Rename the deselect group to plain "Clear selection".

Codex: recommendation is valid. Move census deletion out of the picker into a management surface, and rename the destructive-sounding deselect group to plain selection-clearing copy.

F3Polish

Formatting artifacts in the pickers

  • Census option renders a raw separator token: First Msmt: Sat Feb 02 2008<===> — Last Msmt: …
  • Plot option runs words together: serc— Quadrats: 1600
  • An empty "Other Sites (0)" group renders for global users.
  • Dates appear as Sat Feb 02 2008 in pickers, 2/2/2008 on Census Overview, and Tue Jun 09 2026 15:22:14 GMT-0700 (Pacific Daylight Time) in Uploaded Files — three formats for the same concept.

Fix: one date formatter (e.g. Feb 2, 2008), strip the separator token, add the missing space, hide empty groups.

Codex: recommendation is valid. Use one shared site/plot/census formatter, strip the separator token, fix spacing, and hide empty groups.

F4Polish

The login action is easy to miss

The login page is a full-bleed forest photo with one small dark strip pinned to the bottom-left corner; the avatar bubble overlaps its own label ("U…" behind the circle), and the accessibility audit that runs in dev flags the button for having no accessible name. First-time users on a large monitor can sit on this page looking for what to click.

Fix: a centered card with "Sign in with your Smithsonian account" and a real button label; keep the photo as backdrop.

Codex: revise this. The current login button appears to have an accessible name, so do not cite this as an axe/accessibility failure without a repro. The real issue is visual prominence: make login the obvious primary action.

F5Polish

Navigation appears only after the third selection — silently

Until site, plot, and census are chosen, the sidebar shows only "Dashboard". The full menu materializing after the census pick is good progressive disclosure, but nothing tells the user it will happen — the "Required field for accessing measurement tools" hint exists only as an aria-label. A first-time user may not realize the app has 12 more pages.

Fix: show the nav items disabled with a lock/tooltip ("Choose a census to unlock"), or a one-line hint under the selectors.

Codex: recommendation is reasonable. Prefer visible disabled/locked navigation with short prerequisite hints over silently hiding major sections.

Losing your place

The single biggest source of confusion in the app. It isn't a screen — it's what happens between screens.

F7Critical

Every reload wipes site, plot, and census — and deep links bounce to the dashboard

Selections live in in-memory React reducers. A Zustand store (forestgeo-storage in localStorage) is supposed to persist them, but on boot the empty in-memory state syncs into the store — I watched localStorage go from a full selection to {"state":{}} within two seconds of page load — and nothing ever reads the persisted value back into the contexts. The hub layout then sees no selection and redirects to /dashboard.

Practical impact, reproduced in the walkthrough:

  • F5 anywhere = start over: site → plot → census, every time.
  • URLs like /measurementshub/summary can't be bookmarked, shared, or opened in a new tab — they all land on the dashboard.
  • The GitHub feedback dialog captured "No site selected. No plot selected. No census selected." right after navigation, so bug reports lose their context too (F8).

Fix: on hydration, populate the selection contexts from the persisted store before the layout's redirect guard runs (the hasHydrated flag already exists for exactly this); never write empty state over a non-empty persisted one. Then render sidebar items as real links so tabs and bookmarks work.

Codex: revise this. The current app does persist and hydrate selections through Zustand, so the root cause is not simply in-memory context. Make selection state URL-addressable/bookmark-safe and audit redirect/list-reset timing after hydration.

F8Major

Sidebar navigation is buttons, not links

Nav items aren't anchors: no middle-click, no cmd-click, no "open in new tab", no browser history semantics beyond what the router provides. Combined with F7, multi-tab workflows (errors in one tab, grid in another) are impossible.

Fix: use Next <Link> for nav items; it also gives you prefetching for free.

Codex: recommendation is reasonable. Use real Next links for sidebar navigation where possible, while preserving selection prerequisites.

Trusting the numbers

Scientists calibrate trust in a data tool fast. Three pages currently tell three different stories about the same census.

F9Critical

View Data reports 23,322 unresolved errors; View Errors reports zero

The measurements grid greets you with a warning snackbar — "23322 row(s) with unresolved errors detected" — and its invalid-filter badge agrees. Click the adjacent "View Errors" page and every counter reads 0: Matching rows 0, Validation 0, Ingestion 0. The grid appears to count IsValidated = false rows while the Errors Explorer reads measurement_error_log; the user just sees the app contradicting itself and has no way to find the 23,322 problems it warned about.

Fix: define "unresolved error" once (validation-failed vs error-log-linked), drive both surfaces from it, and make the snackbar a link that lands on View Errors pre-filtered to those rows. If validations simply haven't run yet (the census says "Not Run"), the grid should say "23,322 rows not yet validated" — a completely different message than "errors detected".

Codex: sharpen this. Define separate user-facing states for "not validated," "failed validation," and "unresolved logged error." Then make View Data, snackbar counts, dashboard status, and Errors Explorer use that same taxonomy.

F10Critical

The census stats contradict each other on one screen

Census Overview (and the dashboard) show: 24,324 trees, 33,430 stems, a "1.4 stems per tree" chip — and directly below, Multi-stems: 0. Old trees: 0, New recruits: 33,430 (every stem a first-time measurement), Active personnel: 0. Any forest ecologist will spot that 1.4 stems/tree with zero multi-stem trees is impossible, and will start doubting every other number on the page.

Fix: derive the classification tiles from the same query as the core counts (or fix the classification query); when a metric legitimately can't be computed yet, render "—" with a tooltip, never a confident 0.

Codex: recommendation is valid. Either compute "multi-stem trees" directly from current census data or relabel the current metric as a previous-census cohort comparison. Do not show it as "Trees with multiple stems" unless that is what the query actually computes.

F11Major

"Data Quality: Not Run" is the third version of the story

The same overview says Data Quality "Not Run — validations have not been executed" (0 of 5). So within one census the user can read: 23,322 errors (grid), 0 errors (errors page), and "we haven't checked yet" (overview). Each is defensible in isolation; together they erode confidence.

Fix: a single census-status strip (Validated ✓ / Not yet run / N failing) rendered identically on all three pages.

Codex: recommendation is valid, but note the likely source is placeholder/dashboard status plumbing. Fix by wiring the same validation/run status source used elsewhere.

Working in the grids

The data grids are where users spend their hours. They're functional — inline editing, filtering, and export all work — but density and labeling problems slow every visit.

F12Major

All Historical Data is unreadable out of the box

The 50-plus-column archive grid opens with nearly every header truncated to one or two letters — M…, Pl…, D…, C… — and cell values clipped mid-number (008-02, 99.999). Users must drag-resize a dozen columns before they can tell what they're looking at.

Fix: set sensible min/flex widths per column type, hide low-value columns by default (they're already toggleable via "Columns"), and persist the user's column layout.

Codex: recommendation is sound. Prioritize sensible column widths, default-hidden low-value columns, persistent table density/layout, and no first-load horizontal sprawl.

F13Major

Six unlabeled icon toggles with "99+" badges control what the grid shows

The View Data toolbar's filter row is icon-only: red triangle, green shield, clock, bell, branch, seedling — each with a capped "99+" badge. Their meanings ("Hide invalid measurements (23322)", "Hide new recruits (33430)", …) exist only in aria-labels. The badge caps at 99+, so the one number users actually need (how many invalid rows?) is hidden. Toggling one silently changes what 33k-row pagination means.

Fix: convert to labeled filter chips ("Invalid · 23,322", "Valid · 10,108") with pressed/unpressed states, real counts, and no cap. Chips double as the missing legend for the row-status icons in the first column.

Codex: recommendation is sound. Use labeled state chips with real uncapped counts; they should also explain the row-status icons.

F14Major

The warning snackbar covers the pagination bar; 10 rows per page × 3,343 pages

The unresolved-errors snackbar renders on top of the pager (see F9's screenshot), hiding "Page 1 of 3343" until dismissed. And the default page size of 10 turns this census into 3,343 pages.

Fix: anchor the snackbar above the grid (or as a dismissible banner row), default to 50–100 rows, and remember the user's choice.

Codex: recommendation is sound. Replace snackbar-over-pagination with an anchored banner, raise the default page size, and persist the user's choice.

F15Polish

Manual data entry hides behind an unlabeled clipboard icon

Adding a single record without a CSV is possible — the "Submit data by filling out a form" dialog is well-built, with required/optional chips per field — but its trigger is an anonymous clipboard icon next to the labeled "Upload" button. On the fixed-data grids (Stem Codes, Personnel…) there is no visible "Add" affordance at all; users must discover the same icon.

Fix: a labeled "Add record" button beside "Upload" on every grid.

Codex: recommendation is reasonable. Use a visible "Add record" action on fixed-data grids and a clearly labeled "Manual entry" action on measurement grids.

F16Polish

The header-mapping explainer tops every grid page

"🔄 Understanding Grid and Upload Form Headers" with its "💡 Pro Tip:" banner sits above all seven data grids. It's genuinely useful reference material — the first time. After that it's a permanent tax on vertical space and its emoji-heavy style clashes with the rest of the UI.

Fix: move it into the upload/add dialogs (where the mapping question actually arises) or behind a "?" next to the grid title; drop the emoji.

Codex: recommendation is reasonable. Move recurring header-mapping guidance into upload/add dialogs or contextual help; keep grid pages focused on data.

F17Polish

Per-row irreversible delete, one click from every row

Every row of every grid carries a trash button whose tooltip reads "Delete this row (cannot be undone!)". Whether a confirmation stands between click and deletion I did not test against live data — but the tooltip itself advertises irreversibility instead of safety.

Fix: confirm (with the row's tag/species in the dialog), or better, soft-delete with an undo toast — the changelog infrastructure to support undo already exists.

Codex: revise this. Row deletion is not purely one-click in the current shared grid flow because confirmation exists. Better recommendation: make the confirmation show row-identifying details and add undo/soft-delete where feasible.

History, files & internals

Pages that answer "what happened to my data?" — currently written in the system's voice, not the user's. And one real scoping problem.

F19Critical

Uploaded Files shows other sites' files

Under site Testing Schema → plot serc → census 1, the Uploaded Files page lists CBFDP_SPECIES.csv and CooksBranch_*.csv (Cooks Branch site) and harvard2014.txt (Harvard Forest). The page header explains why: "Accessing Container: plot1-census1" — the blob container is keyed by plot ID and census number only, with no site/schema in the key, so every site whose first plot is ID 1 shares one bucket. Users see files they didn't upload and can't explain; it's also a cross-site data-visibility problem that belongs in your route-authz remediation scope.

Fix: include the schema in the container key ({schema}-plot{id}-census{n}) and migrate existing blobs; replace the "Accessing Container:" header with plain language ("Files uploaded to serc, census 1").

Codex: highest-risk recommendation. Include schema/site identity in uploaded-file container scope, preserve legacy fallback, and plan a migration/backfill. This is both UX and data-isolation/security work.

F20Polish

Uploaded Files speaks Azure, not fieldwork

  • Dates fill three lines: Tue Jun 09 2026 15:22:14 GMT-0700 (Pacific Daylight Time).
  • "Errors in File" column renders blank instead of 0/—.
  • Actions are two unlabeled icons; the delete glyph reads as a backspace key.

Fix: short local dates, an explicit 0/— for errors, labeled Download/Delete actions with confirmation.

Codex: recommendation is valid but should follow F19. Once storage scope is fixed, clean the UI copy: hide Azure container names by default, use readable dates, show 0 or none consistently, and label actions.

F21Polish

Recent Changes renders raw internals

Entries read INSERT file_upload · Record #SERC_c1_from_database.csv followed by a monospace diff dump (+ fileName: …, uploadMode: clean_reupload), attributed to "Stilwell, Mason [Ellevation Education Data Integration Engineer]" — the bracketed Azure AD job title included. The stat filters and layout are good; the entry bodies are log lines.

Fix: template per operation type ("Mason uploaded SERC_c1_from_database.csv — 33,430 measurement rows, clean re-upload"); strip the AD title; keep the raw diff behind an expander.

Codex: recommendation is fair, but the current page is not just a raw table. Add domain-specific change summaries first, and keep raw diffs behind an expander.

F22Polish

Raw SQL is the primary content on two scientist-facing pages

Post-Census Statistics shows each query's SQL in a wide column before its human description, with "No results" everywhere until run. The Validations Hub lists CALL RunSharedDBHChangeValidations(@p_CensusID,…) per rule, and "ADD NEW VALIDATION" drops an inline row demanding a procedure name (placeholder truncated to "Procedur") and hand-written SQL with semicolon-separated criteria — an expert authoring surface presented to every user at full prominence.

Fix: lead with names, descriptions, and last-run results; collapse SQL behind a "view query" expander; gate validation authoring behind an "advanced" affordance with a template picker (the "Use Template" button that exists is the right instinct).

Codex: mostly valid, but note that validation authoring is role-gated. SQL should still be progressive disclosure: show validation name, description, last run/result, and status first; expand SQL for advanced users.

F23Polish

Errors Explorer's empty state looks broken

With zero errors, the table area shows a grey skeleton row and a pager reading "Page  of 0". A clean census deserves a positive empty state, not loading chrome.

Fix: "No unresolved errors in this census ✓" panel; clamp the pager to "Page 1 of 1".

Codex: recommendation is valid. Add a positive empty state and clamp pagination display so empty results do not read as "Page of 0."

Admin

Reachable only by URL as far as I could find, and it swaps the navigation model once you're there.

F24Major

Admin is hard to enter and strange to leave

No sidebar or menu item I encountered links to /admin/* — I reached it by typing the URL. Once inside, the sidebar reduces to "Provision Site / Provisioning Runs / Dashboard" plus the instruction "Select a site to exit admin and go to dashboard:" — selecting a site is the exit mechanism. There's also no link between the admin pages themselves (Sites ↔ Users ↔ Assignments).

Fix: an "Administration" section in the settings/avatar menu for global users; inside admin, a small nav listing the four admin pages and an explicit "← Back to app".

Codex: revise this. Admin entry points already exist for users, sites, and user-site assignments, and provisioning appears inside admin. The better fix is a coherent admin nav shell with "Back to app," plus exposing provisioning consistently.

F25Major

Site Management shows a ghost row and zero sites to a global admin

The grid reports "0–0 of 0" yet renders one half-filled editable row (5 / 5 / mm / m / false with no name) — presumably a new-row template. The same global user sees 9 sites in the selector and 9 in User-Site Assignments; Site Management is the one page that shows none. Headers truncate to "Subqu… / Default… / Doub…".

Fix: populate from the same all-sites source as the selector for global users; render the new-row template only after an explicit "Add site" click.

Codex: recommendation is reasonable. Site Management should not depend on a selected site context if global admins are managing all catalog sites. Show the empty/new-site template only after the user starts adding a site.

F26Polish

User Management: always-armed Save, no add, no dirty state

Every cell is an editable input; "Discard Changes / Save Changes" sit enabled at the top whether or not anything changed; there's no visible way to add a user and no indication of which rows are dirty. User-Site Assignments next door is much stronger (counts, role filter, avatars).

Fix: read-only rows with per-row edit, enable Save only when dirty, add an "Invite user" action.

Codex: revise this. Save/Discard are already dirty-gated. The remaining improvements are row-level edit mode, read-only default rows, clearer changed-row indicators, and an Invite/Add user flow.

Mobile & robustness

Field crews are tablet and phone users by definition.

F28Major

At phone width the app is only a sidebar

At 390×844 the dashboard renders the sidebar full-width with the main content nowhere reachable; the ForestGEO logo clips behind the hamburger button. If tablets/phones are a real usage context for field crews, the selection flow and at least the read-only pages need a responsive pass.

Fix: collapse the sidebar to a drawer at narrow widths and let the dashboard cards stack; or explicitly declare desktop/tablet-only and say so on small screens.

Codex: directionally right. There is a mobile menu toggle, but the active layout is still sidebar-plus-margin rather than a clean drawer. Either implement a proper drawer/tablet layout or explicitly set desktop/tablet support expectations.

F29Polish

Hydration mismatches on most pages; "?" opens a feedback form, not help

Nearly every route logs a React hydration-mismatch error (visible flash risk in prod, and it's what the dev-overlay "2 Issues" badge was counting during the audit). Separately, the floating "?" button — the universal symbol for help — opens the GitHub feedback form; there is no user documentation link anywhere in the app, though a docs site exists.

Fix: chase the typeof window / date-dependent render in the hub layout; make "?" open a small menu: "Documentation" (docs site) + "Report an issue" (the existing form).

Codex: needs more evidence. Hydration mismatch claims should include console output or repro steps. The help/feedback ambiguity is valid: split help/docs from report-feedback.

What's working well

Keep these — several are better than the industry norm for scientific tools.

F30Keep

Six things worth protecting

  • The upload-mode dialog — "Clean Re-Upload (Destructive)" vs "Revisions Upload (Recommended)" with plain-language consequences is excellent risk communication. Only tweak: list the recommended option first.
  • Confirmation modals on the big red buttons — Publish census, Rebuild ViewFullTable, and census deletion all confirm before acting.
  • The read-only banner on All Historical Data — "To edit measurements, use the View Data page; to fix errors, use View Errors" is exactly the right cross-navigation copy; more pages should do this.
  • The provisioning wizard — clear 4-step stepper with real inline validation messages on empty submit.
  • Aria-label coverage — nearly every icon button has a meaningful label (it's how this audit decoded the toolbar); surface those same strings as visible tooltips and you fix F13 half-way.
  • The three-step site → plot → census scoping model — the mental model is right; everything in this report is about smoothing it, not replacing it.

Codex: recommendation is accurate. Keep the upload mode dialog, confirmation modals, read-only banner, provisioning wizard, aria-label/tooltips work, and the site → plot → census selection model.

Method & caveats

Playwright-driven Chromium against npm run dev on 2026-07-06, authenticated through the E2E credentials provider (userStatus: global, no explicit site grants — F1 and F25 are amplified by that profile, but the code paths affect any global user). All walking was read-only: dialogs were opened and dismissed; no uploads, saves, deletes, publishes, or rebuilds were executed. Census: Testing Schema / serc / census 1 — 24,324 trees, 33,430 stems, 1,600 quadrats. Pages visited: login, dashboard, all eight Census Hub pages, four fixed-data grids, four admin pages, plus the upload, manual-entry, add-validation, and feedback dialogs, inline row editing, full-page refresh, direct-URL navigation, and a 390px viewport. Findings F7/F9/F10/F19 were re-verified a second time before being written up. Full-resolution screenshots and the driver scripts are in the session scratchpad (shots/, 0*.mjs).
