Standing up a new ForestGEO site used to be a sequence of manual SQL steps run against the database by an engineer. As of **May 2026**, provisioning happens entirely in the app through a guided wizard at **`/admin/provision`** — admins fill out four short forms and the system handles the schema creation, table seeding, validations, catalog registration, and quadrat generation as a sequence of resumable steps.

:::note
Site provisioning is restricted to users with the **global** role. Reach it from the **gear icon at the bottom of the sidebar** and choose **Provisioning**. If that entry is not in the menu, you do not have access — the sidebar does not show an Administration section until you are already on an admin page.
:::

:::note
**How the schema is built.** Provisioning applies the current table and stored-procedure scripts
directly; it does **not** replay the numbered migration history. Those scripts already describe
the finished shape of the schema, so replaying migrations on top would fail on objects that
already exist.

The practical consequence is that a freshly provisioned site is only as current as those scripts
are. If a schema change has landed as a migration but has not yet been folded into them, a new
site can come out missing it — which will surface as a schema-contract failure at deploy time
rather than during provisioning. If you provision a site and a subsequent deploy complains about
missing objects in it, that is the cause, and it needs engineering rather than a re-run.
:::

### 1 · Site

The first step captures the catalog-level metadata.

| Field | What it is | Notes |
|---|---|---|
| **Site name** | Display name shown in the site selector | e.g. `Rabi` |
| **Schema name** | The MySQL schema that will hold this site's data | Lowercase letters, numbers, underscores only. Must start with `forestgeo_` — e.g. `forestgeo_rabi` |
| **Location** | Locality | Free text |
| **Country** | Country name | Free text |
| **Subquadrat dimensions** | `SQDimX` × `SQDimY` | Defaults to 5 × 5 |
| **Default DBH unit** | `mm` (most common) | Used for upload parsing |
| **Default HOM unit** | `m` (most common) | Used for upload parsing |
| **Double data entry** | Whether measurements must be entered twice to be accepted | Off by default |

:::caution
**Schema name is permanent.** Once provisioning succeeds, you can't rename the schema from the UI. Pick a slug that will read well years from now.
:::

### 2 · Plot

Define the first plot for the new site. You can always add more plots later — this is just the one that gets created during provisioning.

| Field | Notes |
|---|---|
| **Plot name** | Must be unique across the site |
| **Dimensions X × Y** | Plot size in metres (or whatever you set as the default coordinate unit) |
| **Area** | Computed automatically from dimensions |
| **Global X / Y / Z** | The plot's origin coordinates — used by location-based validations |
| **Plot shape** | `square`, `rectangular`, or `irregular`; `square` is the default. The value is recorded for reference and does not change how the wizard validates geometry |
| **Default units** | Dimension, coordinate, area, DBH, and HOM units. Defaults to metric |

### 3 · Quadrats

Three modes are available:

<CardGrid>
  <Card title="Grid mode (regular plots)">
    Specify a quadrat size (e.g. 20 × 20 m) and the wizard will tile the plot automatically. The plot dimensions must be evenly divisible by the quadrat size — if they aren't, switch to CSV mode. A generated grid is capped at 10,000 quadrats.
  </Card>
  <Card title="CSV mode (irregular plots)">
    Upload a CSV of quadrats with `startX`, `startY`, `dimensionX`, `dimensionY`, and `quadratName` columns.
  </Card>
  <Card title="None (add later)">
    Create the site with no quadrats at all and load the real ones afterwards.
  </Card>
</CardGrid>

:::tip
**If you are going to upload your real quadrats later, choose None.** Seeding a placeholder grid
and then uploading the actual quadrats leaves the site holding both sets — which is how one site
ended up reporting twice the quadrats it has. Pick None whenever the grid you would generate is a
placeholder rather than the real layout.
:::

Grid and CSV mode both show a live preview of the layout and surface geometric problems before
you can advance. Rows that fall outside the plot, or a plot whose dimensions are not divisible by
the quadrat size, are hard errors and block the step.

**Overlaps are not.** Real surveyed quadrats sometimes do overlap, so the wizard reports them as a
warning and lets you acknowledge and proceed. Read the warning before accepting it — an
unintended overlap is much easier to fix now than after measurements reference the quadrats.

:::tip
For most established ForestGEO sites the standard 20 × 20 m quadrat grid is correct — start with Grid mode. CSV mode exists for sites that already have an irregular historical layout you want to preserve.
:::

### 4 · Review

The final step summarises everything you entered. Submit to start the run.

## Watching and managing runs

Visit **`/admin/provision/runs`** for a table of every provisioning run with its status and timestamps.

| Status | Meaning |
|---|---|
| **running** | Currently in progress — open the run page to watch step-by-step progress |
| **completed** | Finished successfully; site is live |
| **failed** | A step errored. Open the run to see which step and the error message |
| **aborted** | The run was torn down — either by aborting a failed run, or by deleting the site it created |

A heartbeat worker keeps long-running provisioning alive even across app server restarts; if a run is mid-flight when the server bounces, it will be picked back up automatically.

### Retry and abort

If a run **fails**, the failure detail tells you exactly which step errored. After fixing the underlying cause (e.g. a database connectivity blip), you can retry from the failed step rather than starting over — the steps that already succeeded are not re-run.

**Abort** is only available once a run is `failed` — it drops the half-built schema and clears the
catalog entry, so no orphaned schema is left behind. You cannot abort a run that is still
`running`.

If a run appears stuck, that is what **Mark failed & retry** is for. It becomes available once a
step has been running for more than five minutes, and moves the run into `failed` so you can
either retry it or abort it.

## Deleting a provisioned site

Sites created through the wizard can be **deleted** from the run's status page (`/admin/provision/[runId]`) using the **Delete provisioned site** button. This drops the entire site schema and removes the catalog entry — it is irreversible.

:::danger
Deleting a site **destroys every measurement, plot, census, quadrat, and supporting data row** in that schema. There is no undo. Make sure you have a backup if there's any chance you'll need the data later.
:::

### What "Delete provisioned site" does

1. Verifies the run is in **completed** status — you cannot tear down a run that's still `running`, `failed`, or `aborted` from this button. For a failed run, use **Abort** instead.
2. Checks that no **background upload jobs** for the schema can still run. If any are outstanding, the teardown is refused and tells you how many — wait for them to finish or cancel them first. This stops a job writing into a schema that is being dropped out from under it.
3. Checks that `catalog.sites` holds exactly one row for the schema. If it holds none or several, the teardown stops rather than guessing which to remove.
4. Asks you to **type the exact schema name** (e.g. `forestgeo_rabi`) into the confirmation dialog. This is intentional — a single click can't trigger a teardown.
5. Removes the catalog entries in one transaction, foreign keys first:
   - DELETE any rows in `catalog.usersiterelations` that referenced the site
   - DELETE the row from `catalog.sites`
   - COMMIT
6. **DROP DATABASE** for the schema, outside that transaction and only after the commit succeeds. `DROP DATABASE` cannot be rolled back, which is exactly why it runs last.
7. Logs the teardown to the provisioning audit trail with the username and run ID, and marks the run `aborted`.

Putting the `DROP DATABASE` after the catalog commit guarantees there is **never** a state where the catalog still references a missing schema (no orphans). If anything before the commit fails, nothing has changed and a retry is safe.

### What this **cannot** delete

The teardown button is scoped to **sites that were provisioned through the wizard**. Sites that pre-date the provisioning system don't have a provisioning run associated with them and cannot be deleted from this UI. To remove a legacy site, coordinate with engineering — the catalog row and the underlying schema have to be removed manually with the same `catalog delete → commit → drop schema` order.

### When you'd actually use this

- A test site you stood up to validate the wizard and never plan to use.
- A provisioning run that was completed but used the wrong schema slug; rather than living with the typo forever, delete and re-provision with the correct name.
- A pilot site whose data has already been exported elsewhere and is no longer needed in the live app.

For anything else — a site you want to *empty* without destroying — use **partial census deletion** from the census overview instead. That clears measurements while preserving the site, plot, and supporting data.

## What still needs to happen manually after provisioning

The wizard sets up the **structure**; the **content** still needs to be loaded:

1. **Taxonomy** — load family, genus, species, and any species limits via the standard upload flow.
2. **Personnel & roles** — add the researchers who will be working in this site.
3. **Attributes** — load the site's attribute/stem code definitions.
4. **User access** — for non-global users, add `catalog.usersiterelations` rows so they can see the new site (this is on the admin Users → Sites page).
5. **Measurements** — once supporting data is in place, you can upload the first census's measurements through the normal upload flow.

## Legacy CTFS import

If the new site is being created from a **CTFS legacy `stable_*` schema**, do **not** use the provisioning wizard. The CTFS path is destructive to the target schema and runs a different migration sequence. Coordinate with engineering — there's a separate CLI runner that handles legacy imports.
